01 Setup

This section is still setup. By its end, your program can take whole frames off a cable and put whole frames back on, as raw bytes. That's the floor every later section stands on, starting with Ethernet in 02. Sockets aren't what this book is about, so this section gives you the code: the whole link package is shown and explained line by line. You type it in, make sure you understand it, prove it works with the tests, and then write a small demo of your own that dumps and sends raw frames. Reading takes about 20 minutes.

First, run the setup page's script (sudo ./netsetup.sh setup). You need its test cable here. Its two ends are nw-stack, which is yours, and nw-kernel (10.77.0.1), which belongs to Linux and lives in the network namespace notwork.

1. A raw door to the cable

Why a normal socket won't do

A TCP or UDP socket gives you what's left after the kernel has done all the networking: it has already read and removed the Ethernet, IP and TCP headers, and you only see the payload. Your stack is going to do that work itself, so it needs the frames before the kernel's stack touches them.

Linux has a socket family for exactly that: packet sockets, AF_PACKET. In the man page's words, they "are used to receive or send raw packets at the device driver (OSI Layer 2) level". Opened as SOCK_RAW, a packet socket gives you each frame starting with its Ethernet header. The card has already removed the preamble and the frame check sequence (00, "Where Notwork sits"), so the frame starts at the destination MAC and ends at the last byte of the payload. On Wi-Fi it's Ethernet as Linux presents it (00, section 2).

Where it taps in

  • Receiving: each frame that arrives on the interface is handed to your socket and, as a copy, to the kernel's own stack. The kernel still sees everything. That's why your stack has its own IP address: the kernel ignores traffic that isn't for its own addresses, so it doesn't answer in your place.
  • Sending: a frame you write goes straight to the driver, past the kernel's IP stack and its firewall. Linux adds nothing to it. Whatever bytes you write are the frame.

One frame per read

A packet socket keeps frames apart: each read returns exactly one frame, and each write sends exactly one. If your buffer is smaller than the frame, the rest of the frame is silently cut off and lost. The next read returns the next frame, not the rest of this one (recv(2), under MSG_TRUNC). With offloads off (the setup script does that), a frame is at most 1514 bytes: the 1500-byte MTU plus the 14-byte Ethernet header. So read into a buffer at least that big; 2048 bytes is a common choice.

Privileges

A packet socket sees every frame on the interface, other programs' traffic included, and can send any bytes it likes. So opening one requires the CAP_NET_RAW capability (capabilities(7): "Use RAW and PACKET sockets"). Without it, opening the socket fails with EPERM ("operation not permitted"). There are two ways to get it:

  • Run as root. The tests do: go test -exec sudo ./... builds as you and runs only the finished test binary with sudo.
  • Give one program the capability: sudo ./scripts/netsetup.sh --grant ./raw (it uses setcap(8)). Grant it again after each rebuild, because a new binary is a new file.

Self-check

  1. What does one read on a raw packet socket give you that a read on a TCP socket doesn't?
  2. Which capability does a program need to open a packet socket, and why is it guarded at all?
  3. You read into a 64-byte buffer, and a 98-byte frame arrives. What does the read give you, and what does the next read give you?
Answers
  1. One whole frame, starting with its Ethernet header (destination MAC first), with every header still in it. A TCP socket only gives payload bytes, after the kernel has read and removed all the headers.
  2. CAP_NET_RAW (or running as root). It's guarded because a packet socket sees every frame on the interface, including other programs' traffic, and can send arbitrary frames.
  3. The first 64 bytes of the frame; the other 34 are lost. The next read gives the next frame, not the rest of this one.

2. The link package

Here is the whole package, src/link/link.go, in three pieces. Type it in rather than pasting it, and make sure every line makes sense to you: the explanations come after each piece. (You don't need to know Go well for this: most of the package is four system calls and a little wrapping.)

The file's top

// Package link is a raw link on one network interface: whole Ethernet frames
// in and out, as bytes, through a Linux packet socket (packet(7)).
package link

import (
	"encoding/binary"
	"fmt"
	"net"
	"os"
	"time"

	"golang.org/x/sys/unix"
)

// htons turns a 16-bit number from the CPU's byte order into network byte
// order (big-endian), which is what packet(7) wants for protocol numbers.
func htons(v uint16) uint16 {
	var b [2]byte
	binary.BigEndian.PutUint16(b[:], v)
	return binary.NativeEndian.Uint16(b[:])
}
  • golang.org/x/sys/unix is Go's maintained package for Linux system calls and constants. The standard library's syscall package is frozen and points to it.
  • htons means "host to network, short" (a 16-bit number), the classic C name. packet(7) says the protocol is "the IEEE 802.3 protocol number in network byte order". ETH_P_ALL is 0x0003 ("every protocol"). On your little-endian CPU, its two bytes have to be swapped before the kernel reads them as a native number. That's the layout-versus-value point from 00, section 3. x/sys/unix passes Protocol through unchanged, so the swap is your job. Forget it, and you're asking for EtherType 0x0300, which never arrives, so the socket stays silent.

Conn and Open

// Conn is a raw link on one interface: an open packet socket, bound to it.
type Conn struct {
	f *os.File // the socket, handed to Go's runtime
}

// Open opens a raw link on the interface named ifname: every EtherType,
// frames from that interface only, outgoing frames ignored.
func Open(ifname string) (*Conn, error) {
	// 0. The kernel knows interfaces by index, not by name: look it up.
	ifi, err := net.InterfaceByName(ifname)
	if err != nil {
		return nil, fmt.Errorf("open %s: %w", ifname, err)
	}

	// 1. A raw packet socket. Protocol 0 means "receive nothing yet", so no
	//    frames from other interfaces sneak in before we bind. SOCK_NONBLOCK
	//    lets Go's runtime wait on it; SOCK_CLOEXEC keeps it out of programs
	//    this one starts.
	fd, err := unix.Socket(unix.AF_PACKET, unix.SOCK_RAW|unix.SOCK_NONBLOCK|unix.SOCK_CLOEXEC, 0)
	if err != nil {
		return nil, fmt.Errorf("open %s: socket: %w", ifi.Name, err)
	}

	// 2. Only hand us the frames that arrive, not the ones that leave
	//    through this interface (ours or the host's).
	err = unix.SetsockoptInt(fd, unix.SOL_PACKET, unix.PACKET_IGNORE_OUTGOING, 1)
	if err != nil {
		unix.Close(fd)
		return nil, fmt.Errorf("open %s: ignore outgoing: %w", ifi.Name, err)
	}

	// 3. Bind to this one interface, and start receiving every EtherType.
	addr := &unix.SockaddrLinklayer{
		Protocol: htons(unix.ETH_P_ALL),
		Ifindex:  ifi.Index,
	}
	if err := unix.Bind(fd, addr); err != nil {
		unix.Close(fd)
		return nil, fmt.Errorf("open %s: bind: %w", ifi.Name, err)
	}

	// 4. Hand the fd to Go. Because it's non-blocking, the *os.File is
	//    "pollable": Read and Write wait in the runtime instead of blocking
	//    a thread, and read deadlines work.
	f := os.NewFile(uintptr(fd), "packet:"+ifi.Name)
	return &Conn{f: f}, nil
}
  • Conn holds one thing: the socket, as an *os.File (step 4 explains why a file). Wrapping it in a type of its own means a Conn offers exactly the four methods a link needs, and nothing a file has that makes no sense for a link (seeking, file names, ...).
  • Step 0, the lookup. The kernel names interfaces by index, a small number, not by name. ip link prints the index at the start of each line. net.InterfaceByName turns the name into a *net.Interface (ifi), which holds the index, the name and the MAC address. It's the first thing that can fail, for a name that doesn't exist, and no socket exists yet to clean up.
  • Step 1, socket (socket(2)). The protocol argument is 0 on purpose. packet(7): "If protocol is set to zero, no packets are received. bind(2) can optionally be called with a nonzero sll_protocol to start receiving packets for the protocols specified." If you opened it with ETH_P_ALL straight away, it would receive from every interface until the bind, and the first frames you read might come from somewhere else.
  • Step 2, PACKET_IGNORE_OUTGOING (Linux 4.20 and later; the option is defined in if_packet.h). By default, a packet socket also sees every frame that leaves through the interface: the ones the host sends, and your own. packet(7) calls these PACKET_OUTGOING. Your stack would read back each frame it wrote as if someone else had sent it. This option turns that off, so your stack only sees what arrives.
  • Step 3, bind (bind(2)). packet(7): "Only the sll_protocol and the sll_ifindex address fields are used for purposes of binding." That's where the index from step 0 goes. After the bind, a plain write on the socket sends out of this interface, and reads only return frames from it.
  • Step 4, os.NewFile (docs): "If fd is in non-blocking mode, NewFile will attempt to return a pollable File (one for which the SetDeadline methods work)." So with SOCK_NONBLOCK from step 1, the *os.File already knows how to read, write, close and time out, one whole frame at a time. From here on, the *os.File owns the fd, and closing the file closes the socket.
  • The error paths close the fd by hand, because until step 4 nothing else owns it. Without that, a failed Open would leak a socket. Each error says which interface and which step failed, and wraps the system call's error with %w, so a caller can still check it (e.g. errors.Is(err, unix.EPERM) when the capability is missing).

The four methods

// Read waits for the next frame that arrives and copies it into b. Each call
// returns one whole frame; a frame longer than b is cut to len(b).
func (c *Conn) Read(b []byte) (n int, err error) {
	return c.f.Read(b)
}

// Write sends frame, unchanged, as one frame. It must start with the
// Ethernet header; the card adds the FCS.
func (c *Conn) Write(frame []byte) (n int, err error) {
	return c.f.Write(frame)
}

// SetReadDeadline makes a Read that is waiting at t, or called after it,
// fail with os.ErrDeadlineExceeded. The zero time means no deadline.
func (c *Conn) SetReadDeadline(t time.Time) error {
	return c.f.SetReadDeadline(t)
}

// Close closes the socket. A Read waiting in another goroutine returns
// with an error.
func (c *Conn) Close() error {
	return c.f.Close()
}
  • Each method hands the call to the *os.File. All the real work happened in Open: the socket already keeps frames apart (section 1), so a file read is one frame and a file write is one frame.
  • Waiting happens in Go's runtime, thanks to step 4: a Read with nothing to read parks its goroutine until a frame arrives, the deadline passes (os.ErrDeadlineExceeded), or another goroutine calls Close, which wakes it with an error. That last one is how a program stops a reader cleanly.

Self-check

  1. Answer in hex: on your little-endian machine, which 16-bit number does htons(0x0003) return?
  2. Why does step 1 open the socket with protocol 0 instead of ETH_P_ALL?
  3. Without step 2, what would your stack read right after it writes a frame?
  4. What would you lose if the socket weren't opened with SOCK_NONBLOCK?
Answers
  1. 0x0300: the two bytes are swapped, so that in memory they lie as 00 03, network byte order.
  2. With protocol 0 the socket receives nothing until bind sets the protocol and the interface. With ETH_P_ALL at socket time, it would receive frames from every interface in the moment before the bind.
  3. Its own frame: by default a packet socket also sees outgoing frames (its own and the host's), so the stack would read back what it just sent, as if someone else had sent it.
  4. The *os.File wouldn't be pollable: read deadlines wouldn't work (a read could block forever), and each blocked read would tie up an OS thread instead of waiting in Go's runtime.

3. The demo: cmd/raw

This is the part you write. It's a small program that uses your link package to do two things a network card does all day: put one frame on the cable, and show you every frame that comes off it. No flags or arguments: what it works on is written into the program as two constants.

Where it lives

One file, src/cmd/raw/main.go, in package main. It uses your package by importing notwork/link (the module's name, then the folder).

What it does, in order

  1. Two constants at the top of the file: the interface to use, "nw-stack", and the text to send, e.g. "hello from my stack". To try it on your real network later, you change the first one to "wlan0" (or your wired interface) and build again.
  2. Find your own MAC address. The frame you send has to say who sent it, and that's the interface's MAC. Look the interface up by name, the same way Open's step 0 does: the *net.Interface you get back has it, in HardwareAddr.
  3. Open a link on the interface with link.Open.
  4. Build one frame and send it with Write. A frame is just bytes, one after the other:
    BytesWhat you put thereWhat it means
    0–5six bytes ffTo: everyone on the cable (the broadcast address)
    6–11your MAC, from step 2From: you
    12–1388 b5What kind of frame this is (the EtherType)
    14 onwardthe bytes of your textThe message
    0x88B5 is an EtherType IEEE reserves for "local experimental" use (IEEE EtherType registry), so no real protocol will mistake your frame for one of its own. What these first 14 bytes are, field by field, is what 02 is about.
  5. Then print every frame that arrives, forever, until you stop the program with Ctrl-C. Read into a 2048-byte buffer (section 1, "One frame per read"). For each frame, print one line with its length, then its bytes in hex. Go's hex.Dump prints that layout for you, so you don't have to format anything. One frame looks like this (your MAC addresses will differ): 
    42 bytes
00000000  ff ff ff ff ff ff 02 4b  1c 9e 30 01 08 06 00 01  |.......K..0.....|
00000010  08 00 06 04 00 01 02 4b  1c 9e 30 01 0a 4d 00 01  |.......K..0..M..|
00000020  00 00 00 00 00 00 0a 4d  00 02                    |.......M..|
    The left column is the offset of the line's first byte (in hex), then 16 bytes, then the same bytes as text where they're printable. You'll see the first 6 + 6 + 2 bytes have the same shape as the frame you built in step 4.

If anything fails (the interface doesn't exist, the program lacks the capability, a read fails), print the error and stop. log.Fatal does both.

You won't see your own frame in the output: the link ignores frames that leave the interface (section 2, step 2). To see it, you watch from the other end of the cable (section 5).

Hint 1: the read tests time out without seeing a single frame

Watch the cable from the kernel's side while the test runs: sudo ip netns exec notwork tcpdump -i nw-kernel -e -n. If tcpdump shows frames that your Read never gets, the problem is in the socket. Only print buf[:n], never the whole buffer. Ignoring outgoing frames happens in the socket (step 2), not in your demo. If you see your own frames, check that step 2 is there.

Checks your demo cmd/raw against section 3. It can't open sockets, so run the show-off in section 5 yourself, and mention what you saw if something's off. For the link package, the tests are the check: go test -exec sudo ./link/.

5. Verification

Oracle 1: interop with the kernel (the tests)

The kernel on the other end of the cable is the source of truth. It sends frames you didn't make, and it reacts only to frames that are byte-for-byte right. The tests in src/link/link_test.go run in this order:

  1. Unknown interface: Open of a name that doesn't exist fails. This one needs neither root nor the cable.
  2. Open and close nw-stack.
  3. Deadline: on the quiet cable, a Read with a 200 ms deadline gives up after about 200 ms, with os.ErrDeadlineExceeded.
  4. Read a real frame: the kernel pings 10.77.0.2. It doesn't know which MAC address goes with that IP, so it first broadcasts a question about it (that's ARP, section 03). Your Read must return that frame intact: 42 bytes, sent to the broadcast address, from nw-kernel's MAC.
  5. Write a real frame: the test writes, through your Write, a question it built itself: "who has 10.77.0.1?". The kernel only answers a correct frame, so the answer arriving proves your frame left intact. Your own question must never come back to Read.
  6. Read after close fails, and doesn't block.

They skip, with a message, when they're not run as root or when nw-stack doesn't exist. Add -v to see which ran.

Oracle 2: the real world (the show-off)

Build the demo and give it the capability, from src/ (grant it again after every build):

go build -o raw ./cmd/raw
sudo ./scripts/netsetup.sh --grant ./raw
  • Frames out, on the cable. In one terminal, watch the kernel's end of the cable: sudo ip netns exec notwork tcpdump -i nw-kernel -e -xx. In another, run ./raw. tcpdump prints your frame: your MAC, the broadcast address, ethertype Unknown (0x88b5), and your text in the hex.
  • Frames in, on the cable. Leave ./raw running. In a third terminal, make the kernel talk: sudo ip netns exec notwork ping 10.77.0.2. A frame appears in your demo about once a second: the kernel asking who has 10.77.0.2, like the example in section 3. Nobody answers yet. That's 03.
  • Frames in, on your real network. Change the interface constant to "wlan0" (or your wired interface; ./scripts/netsetup.sh --status shows which one), build, grant, and run it again. Your LAN's chatter streams in: broadcasts, multicast announcements, traffic to your machine. Compare it with sudo tcpdump -i wlan0 -xx: the bytes match. tcpdump also shows what your machine sends, and your demo doesn't, because of step 2. Put the constant back to "nw-stack" afterwards.

6. Out of scope

  • Memory-mapped rings (PACKET_RX_RING, TPACKET_V3; packet_mmap): the kernel and the program share a buffer, so there's no system call per frame. Real capture tools use them to keep up with fast links.
  • BPF filters (SO_ATTACH_FILTER; kernel docs): the kernel drops unwanted frames before they reach the socket. tcpdump compiles its filter expressions into these.
  • Promiscuous mode (PACKET_ADD_MEMBERSHIP, packet(7)): asks the card to deliver frames addressed to other machines, too. Sniffers on shared networks need it; your stack only cares about its own traffic.
  • VLAN tags and other aux data (PACKET_AUXDATA): on many cards the kernel strips VLAN tags before you see the frame, and a real stack reads them back from aux data.
  • Timestamps (SO_TIMESTAMPNS; kernel docs): when exactly each frame arrived. Capture tools record it.
  • SOCK_DGRAM packet sockets ("cooked" mode): the kernel removes and builds the Ethernet header for you, which would skip the next section.
